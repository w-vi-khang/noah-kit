# Agent Workflow

Reader: maintainers of Noah Kit and of projects that use it. This document explains the design of the main-agent workflow. The enforceable requirements are in `.claude/rules/main-agent.md` and the agent definitions in `.claude/agents/`; this document does not restate them.

## Goal

Spend process in proportion to risk. A small task must not pay for planning, review, and verification it does not need. A large or safety-critical task must not skip them.

## Roles

- **Main agent (MA)**: the session the user talks to. It classifies each request, decides which stages run, delegates to subagents, integrates their results, commits, and reports. It is the only role that talks to the user, commits, or decides scope.
- **Subagents**: one per stage, each with a narrow role, its own tool boundary, and a default model and effort level.

| Stage | Agent | Can edit | Default model / effort | Why this default |
| --- | --- | --- | --- | --- |
| Plan | `planner` | No | opus / high | Planning errors are the most expensive to fix later. |
| Implement | `implementer` | Owned files only | sonnet / high | Executes a plan that is already decided. |
| Test | `test-engineer` | Test files only | sonnet / high | Rationale: a separate test author is less likely to write tests shaped to the implementation. |
| Review | `reviewer` | No | opus / high | Independent judgment needs the strongest model. |
| Verify | `verifier` | No | sonnet / medium | Runs checks and compares results; little open-ended reasoning. |

The MA can override a subagent's model or effort for a single request.

## Default model for the main agent

This repository sets `"model": "claude-opus-5-5"` and `"effortLevel": "high"` in the committed `.claude/settings.json`. A user can change this for themselves without editing the shared file:

- for one project: the same keys in `.claude/settings.local.json`;
- for one session: `claude --model <model> --effort <level>`;
- during a session: `/model` and `/effort`.

## How tiers map to the original workflow

The original vision defines ten steps: understand, clarify, plan, select skills and agents, implement, test, review, address findings, verify, report. Tiers decide which of these run as separate stages:

- **All tiers** run understand, clarify (only when ambiguity changes the result), and report.
- **T0** stops after a self-check of the diff.
- **T1** adds tests run by the MA. The test output, not the MA's opinion, is the verification evidence.
- **T2** adds a separate test author and an independent reviewer.
- **T3** adds a dedicated planner, user approval of the plan, and a verifier that checks the final committed state.

Tier criteria are concrete (file counts, interface changes, named safety-critical areas) so that two runs on the same request choose the same tier.

## Independence and loop prevention

- **No self-approval**: reviewers and verifiers receive the diff and acceptance criteria, not the implementer's conclusions. Read-only agents have no Edit or Write tools.
- **No nested delegation**: no subagent has the `Agent` tool, so subagents cannot start other subagents.
- **Bounded retries**: review-and-fix stops after two rounds and returns to the user.
- **Single writer of history**: only the MA commits, and it does not push unless the user asks.

## Limitations

These are instructions to the model, not enforced controls:

- Tier choice, stage selection, and briefs depend on the MA following `.claude/rules/main-agent.md`. Nothing blocks a skipped stage.
- Read-only agents have Bash, so they could still modify files. Their instructions forbid it, but nothing enforces it.
- No hooks exist yet. `CLAUDE.md` forbids executable hooks until a safety contract and tests exist. Hooks could later enforce a verification gate or block subagent commits.
- No skills exist yet. The MA rule allows using skills once they are defined.
- The structural test (`test/agents.test.js`) checks agent fields, tool boundaries, and that the rule names every agent. It does not test how the model behaves in a real session.

## Distribution to other projects

Today the rule, agents, and settings exist only in this repository. Projects initialized with `noah init` do not receive them. Two options are open:

1. **Generated by `init`**: copy the files into the project's `.claude/`. This is simple, but every project keeps its own copy, and updates need a refresh mechanism, which is also needed for the existing project rule.
2. **Claude Code plugin**: ship agents, rules, skills, and later hooks as a versioned plugin. Plugin agents load at the lowest priority under a scoped name (for example `noah-kit:reviewer`), so a project can override them. This fits the Core/Project separation, but it needs research and a decision on how it relates to the CLI's own versioned installation.

Choosing between them is a pending decision tracked in `docs/implementation-plan.md`.
